# Поиск по фото (OCR этикетки) — дизайн

Дата: 2026-07-12
Ветка: `feat/photo-search`

## Цель

Дать пользователю возможность сфотографировать этикетку напитка и найти
соответствующую запись в дневнике. Распознанный текст этикетки прогоняется
через текстовый поиск по коллекции. Фича оффлайн, без сети и облака.

Смысл «поиска по фото» здесь — **OCR этикетки → текстовый поиск**, а не
визуальное сходство (embeddings) и не автозаполнение новой записи. Эти
сценарии сознательно вне scope (см. «Вне scope»).

## Ограничение

ML Kit on-device text recognition поддерживает только 5 скриптов: Latin,
Chinese, Devanagari, Japanese, Korean. **Кириллического распознавателя не
существует** (пакета `com.google.mlkit:text-recognition-cyrillic` нет в
Maven-репозитории Google). On-device Latin-распознаватель не распознаёт
кириллицу.

Следствие: фича работает **только на этикетках с латинским текстом**
(импортные вина, виски, пиво и т.п.). На кириллических этикетках распознаватель
вернёт пустую строку или мусор — query станет пустым, экран покажет обычное
состояние (фича «не молчит»). Это осознанное ограничение текущей фазы.

Cloud Vision (кириллица + всё) как fallback при наличии сети — возможная
будущая фаза через тот же порт `LabelRecognizer`; вне scope текущей работы.

## Общий поток

1. Пользователь нажимает кнопку-скан в строке поиска на главном экране.
2. Проверяется/запрашивается разрешение `CAMERA`, открывается камера
   (`ActivityResultContracts.TakePicture`), снимок пишется во **временный** файл
   в `cacheDir/camera/` через уже настроенный `FileProvider`.
3. `LabelRecognizer` прогоняет фото через ML Kit **Latin-распознавателем**
   (кириллица on-device не поддерживается — см. «Ограничение»).
4. Текст кладётся в `filter.query` через существующий
   `ListViewModel.onQueryChange(...)`.
5. Уже реактивный поиск пересчитывает список.
6. Временный файл удаляется после распознавания (в `finally`).

Строка поиска остаётся редактируемой: пользователь видит распознанный текст и
может его поправить. При пустом результате распознавания query становится
пустым — обычное состояние экрана, фича «не молчит».

### Обработка ошибок и очистка

`onScanLabel` строится так:

```
if (scanning) return          // защита от двойного запуска
scanning = true
try {
    val text = recognize(source)   // может бросить или вернуть ""
    onQueryChange(text)
} catch (e) {
    // query НЕ трогаем; опционально snackbar
} finally {
    удалить временный файл
    scanning = false
}
```

- Исключение ML Kit → `query` остаётся прежним, `scanning` сбрасывается, файл
  удаляется.
- Отмена съёмки в камере (`TakePicture` вернул `false`) → `onScanLabel` не
  вызывается; временный файл, как и в существующем `EditScreen`, оставляем на
  очистку кэша ОС.

## Стыковка с поиском (вариант A: единый токенизированный поиск)

Ключевое решение: у OCR и у ручного ввода **один путь**. Распознанная
«простыня» из многих слов не найдётся одним `LIKE '%…%'`, поэтому текстовый
поиск переводится на токены.

### Изменения

- **`EntryDao.observeFiltered`**: убрать условие
  `AND (:query = '' OR searchText LIKE '%' || :query || '%')` и параметр
  `query`. SQL продолжает фильтровать по категории, фасетам, цене, рейтингу и
  сортировать как прежде.
- **`EntryRepositoryImpl.observeEntries`**: после получения
  `List<EntryEntity>` — если `filter.query` не пуст:
  - токенизировать запрос через `tokenizeQuery`;
  - оставить записи, где `entity.searchText` **содержит как подстроку**
    (`searchText.contains(token)`, консистентно с прежним `LIKE '%token%'`)
    **хотя бы один** токен (порог ≥ 1);
  - отсортировать **стабильно** по числу совпавших токенов по убыванию;
    tie-break — существующей SQL-сортировкой (`filter.sort`, затем
    `createdAt DESC`), которая сохраняется благодаря стабильности сортировки
    (`sortedWith` в Kotlin стабилен);
  - матчинг идёт по `entity.searchText` **до** маппинга в domain: `searchText`
    в domain-модель по-прежнему не течёт;
  - при пустом `filter.query` — поведение ровно как сейчас (SQL-фильтр +
    SQL-сортировка, без пост-обработки).

**Следствие (одобрено):** при активном поиске порядок результатов — по
релевантности (числу совпавших слов), а не по дате/рейтингу. Для многословных
запросов это плюс; это осознанное изменение прежнего поведения. Индикатор
«сортировка: релевантность» в UI — вне scope, заметка на будущее.

**Trade-off масштаба:** при активном запросе текстовый матчинг уходит из SQL в
память — все строки, прошедшие категорию/фасеты, грузятся и фильтруются в
Kotlin. Для личного дневника (сотни, максимум единицы тысяч записей) это
приемлемо. При пустом query пост-обработки нет, поведение как прежде.

### Токенизация

Чистая функция в domain:

```kotlin
fun tokenizeQuery(text: String): List<String>
```

Правила:
- split по не-буквенно-цифровым разделителям (Unicode-aware, чтобы кириллица не
  считалась разделителем);
- `lowercase`, уникальные;
- отбросить токены короче 3 символов;
- отбросить **чисто числовые токены короче 4 символов** — крепость (`40`) и
  объём (`700`) шумят и не несут смысла, но 4-значные числа (винтажные года
  `2014` в названии) сохраняем, иначе теряется ручной поиск по году
  (`vintageYear` в `searchText` не входит, год ищется только когда он в `name`).

Одна и та же функция применяется к OCR-тексту и к ручному вводу.

**Fallback короткого запроса:** если токенизация дала пустой список (запрос из
коротких символов, напр. инкрементальный набор «ба»), репозиторий падает на
подстрочный поиск по всему запросу — иначе набор первых 1–2 символов показывал
бы пустой экран. Исключение: чисто числовой короткий запрос («40», «700») —
шум крепости/объёма, остаётся без совпадений. Реализовано в `searchTerms`
(`EntryRepositoryImpl`), матчинг единообразно через `matchCount`.

Стоп-слова (vol, alc, product и т.п.) **не** отсекаются: лишние токены просто не
находят совпадений и ранжированию не мешают. Стоп-лист — на потом, если появится
шум.

## Компоненты

### `domain/LabelRecognizer.kt` (новый порт)

```kotlin
interface LabelRecognizer {
    /** Распознаёт текст этикетки из изображения. Пустая строка — ничего не найдено. */
    suspend fun recognize(source: PhotoSource): String
}
```

Переиспользует существующий value class `PhotoSource(val locator: String)`.
Мокается на JVM. Без android-импортов (пройдёт `ArchitectureTest`).

### `platform/AndroidLabelRecognizer.kt` (реализация)

- `TextRecognizer` ML Kit: Latin (`TextRecognizerOptions.DEFAULT_OPTIONS`).
  Клиент — `Closeable`; создаётся и закрывается **на каждый вызов** (сканы редки,
  нет удерживаемой в памяти нативной модели на весь жизненный цикл процесса).
- `InputImage.fromFilePath(context, uri)` из `PhotoSource.locator` (ktx `toUri()`).
- Прогоняет фото через распознаватель, возвращает `.text`.
- Hilt: провайдер + `@Binds` в `BindsModule` (по образцу `PhotoStorage`).
- Сырой `.text` содержит переносы строк между блоками; `ListViewModel.onScanLabel`
  схлопывает пробельные последовательности перед записью в однострочную строку
  поиска.

### `tokenizeQuery` (новая чистая функция)

Расположение — рядом с доменной логикой поиска (domain). Без зависимостей от
Android, полностью JVM-тестируема.

## UI

- В `ListViewModel` — отдельный `MutableStateFlow<Boolean>(false)` для `scanning`,
  **включённый в `combine(...)`** для `state` (state — производный StateFlow, его
  нельзя мутировать напрямую; см. M1).
- `ListState` получает поле `scanning: Boolean`.
- `ListViewModel.onScanLabel(source: PhotoSource)` — по схеме из «Обработка
  ошибок»: guard от двойного запуска, `recognize`, `onQueryChange`, очистка и
  сброс флага в `finally`.
- `ListScreen`: иконка-скан в строке поиска. Захват, разрешение `CAMERA` и запуск
  `TakePicture` вынесены в общий composable-хелпер `rememberCameraCapture(onCaptured)`
  в `ui/util/CameraUri.kt` (рядом с `createCameraUri`) и переиспользуются в
  `EditScreen` (импорт фото записи) и `ListScreen` (скан этикетки) — без дублирования
  оркестрации. Индикатор при `scanning`. При отказе в разрешении — toast.

## Зависимости и данные

- ML Kit: `com.google.mlkit:text-recognition` (bundled Latin-модель, ~4 MB к
  APK). Прописать в `libs.versions.toml` и `app/build.gradle`.
- **Инфраструктура камеры уже есть**: `CAMERA` permission и `FileProvider`
  (`${applicationId}.fileprovider`, `file_paths.xml` с `cache-path camera/`)
  зарегистрированы в манифесте для импорта фото записей. Добавлять не нужно.
- **Миграций Room нет** — колонка `searchText` уже существует, схема не
  меняется. `fallbackToDestructiveMigration` остаётся как есть (dev-стадия).

## Тестирование

- `tokenizeQuery` — JVM unit-тесты: порог длины (< 3 отброшены), отброс коротких
  чисел (`40`, `700`), **сохранение 4-значного года** (`2014`), дубли,
  кириллица → lowercase, пустой ввод.
- Матчинг/ранжирование в `EntryRepositoryImpl` — Robolectric + Room (по
  заведённому в проекте способу): порог ≥ 1, порядок по релевантности,
  **стабильный tie-break по `sort`** (две записи с равной релевантностью
  сохраняют SQL-порядок), пустой query = прежнее поведение.
- **Перенос DAO-тестов (must-do, не «переезд»):** удаление параметра `query` из
  `observeFiltered` ломает 8 call-sites в `EntryDaoTest.kt` — их правим; два
  текстовых кейса (поиск по стране `итал`, по сорту `сира`) **переносим** в
  `EntryRepositoryImplTest`, а не удаляем.
- `LabelRecognizer` — мок в `ListViewModelTest`: `onScanLabel` кладёт
  распознанный текст в query и сбрасывает `scanning`; двойной вызов при активном
  `scanning` игнорируется. Существующие VM-тесты поиска (`FakeRepo` на
  `name.contains`) не ломаются.
- `AndroidLabelRecognizer` — ML Kit на JVM не поднять, автотеста нет; проверка
  ручная на устройстве (в т.ч. на 3–5 реальных латинских этикетках — убедиться,
  что распознанный текст ищется в коллекции).
- **`ArchitectureTest` (Konsist)** — прогнать: `LabelRecognizer` в domain без
  android-импортов, реализация в platform, VM инжектит только domain-порт.

## Вне scope (YAGNI)

- Стоп-слова.
- Визуальное сходство / image embeddings.
- Автозаполнение полей новой записи по фото.
- Выбор изображения из галереи (только съёмка камерой).
- Индикатор «сортировка: релевантность» при активном поиске.
- Облачный OCR (Cloud Vision) для кириллицы при наличии сети.
