# Облачное распознавание этикеток и черновик заметки

**Дата:** 2026-08-27
**Статус:** реализовано в ветке `feat/llm-recognition`, влито в `main`

Решения, изменённые по ходу работы, отмечены ниже как «по итогам проверки»;
изменённые ревизией качества после влития — как «по итогам чистки».

## Контекст

Скан этикетки работает на ML Kit on-device (`AndroidLabelRecognizer`, latin-распознаватель)
и **не читает кириллицу**: на русской этикетке возвращает пустую строку или мусор.
Ограничение зафиксировано в комментарии реализации и в спеке `2026-07-12-photo-search-design.md`.
Для журнала, где заметная часть коллекции — российское вино, поиск по фото фактически
не работает.

Облачная vision-модель кириллицу читает и, в отличие от OCR, возвращает не простыню
текста, а структуру: название и тип. Она же открывает второй сценарий, текстовый:
черновик заметки о вкусе.

### Почему OpenRouter, а не OpenAI или Anthropic напрямую

Разбор путей доступа (сессия 2026-08-27):

- **OAuth к подписке невозможен.** Подписка ChatGPT Plus/Pro и Claude Pro/Max не даёт
  API-доступа: это отдельные продукты с отдельным биллингом. Anthropic в феврале-марте
  2026 закрепил это и политикой, и серверным энфорсментом — OAuth подписки предназначен
  только для Claude Code и claude.ai, использование токена в стороннем продукте
  запрещено, включая их собственный Agent SDK.
- **Схема сторонних харнессов не переносится.** Pi, opencode и подобные читают
  `~/.claude/.credentials.json`, оставленный первопартийным CLI на той же машине.
  На Android такого файла нет — переиспользовать нечего.
- **OpenRouter** даёт один ключ ко всем моделям и OpenAI-совместимый API. Модель
  становится строкой в настройках, а не переписыванием интеграции. Наценки на токены нет;
  комиссия 5.5% берётся при пополнении кредитов.

**Ввод ключа — руками, без OAuth.** У OpenRouter есть штатный OAuth PKCE, но он стоит
intent-filter, Custom Tabs, обмена кода и непроверенного риска с callback-схемой на
Android — порядка двухсот строк ради одной операции копирования. Апгрейд позже ничего
не сломает: кнопка «Подключить» встанет рядом с тем же полем и запишет ту же настройку.

## Область

**Входит:** доменная модель результата распознавания, облачный распознаватель и генератор
черновика, раздел в настройках, два сценария (поиск по фото и черновик заметки), тесты.

**Не входит:** OAuth PKCE, свой бэкенд, выбор модели из списка (модель — текстовое поле),
кэширование ответов, распознавание нескольких этикеток на одном снимке, изменения формата
поста для ВК (`PostText.kt` не трогается).

## Домен

`LabelRecognizer.recognize` возвращает не `String`, а структуру. Поля названы как в `Entry`:

```kotlin
data class LabelScan(
    /** Сырой текст: ML Kit заполняет только его, облако — по возможности тоже. */
    val rawText: String = "",
    val name: String? = null,
    val wineType: String? = null,
    /** «Тип» — своё поле у каждой категории: у пива стиль, у крепкого вид напитка. */
    val style: String? = null,
    val type: String? = null,
) {
    /** Пусто — распознать не удалось; вызывающая сторона показывает «не прочиталось». */
    val isEmpty: Boolean get() = rawText.isBlank() && name == null
}
```

**Состав полей сокращён по итогам чистки.** Изначально структура зеркалила `Entry`
целиком (`producer`, `vintageYear`, `country`, `grapes`, `color`, `sweetness`,
`abvPercent`) ради предзаполнения записи. Предзаполнение отменено, и эти семь полей
никто не читал: они только раздували промпт и выходные токены. Остались те, из которых
собирается поисковый запрос. Вернутся вместе с предзаполнением — строкой на поле
здесь и строкой в промпте.

Рядом — второй интерфейс, для текста:

```kotlin
/** Черновик заметки. [examples] — прежние заметки автора, образец стиля. */
interface DraftWriter {
    suspend fun draftNote(entry: Entry, examples: List<String>): String
}
```

Отказ у него **всегда исключение**, пустой строки он не возвращает: два канала отказа
заставляли каждого вызывающего изобретать своё правило для пустоты, и «распознавание
выключено» приходило к пользователю как «не удалось распознать этикетку» (исправлено
по итогам чистки).

Оба живут в `domain`, без Android-типов и без сетевых — `ArchitectureTest` требует
`domain.dependsOnNothing()`.

## Реализации

`platform/OpenRouterClient` — один HTTP-клиент, `kotlinx.serialization` для тел
запросов и ответов (сериализация уже в проекте). Два метода:
vision-запрос с изображением и текстовый запрос.

Настройки клиент читает сам, а не принимает `RecognitionConfig` параметром: гейт
«облако настроено» должен быть один на всех вызывающих. Изначально его делал только
`OpenRouterDraftWriter`, а `OpenRouterLabelRecognizer` держался на том, что его
единственный вызывающий — делегат (исправлено по итогам чистки). Ненастроенное облако
теперь отказывает причиной `DISABLED`, одинаково для обоих сценариев.

Транспорт — `HttpURLConnection` из stdlib: OkHttp в графе зависимостей отсутствует,
и тащить его ради одного POST незачем (проверено `:app:dependencies`). Поверх него — `OpenRouterLabelRecognizer`
и `OpenRouterDraftWriter`.

Схему просим промптом, а не `response_format`: не все модели каталога поддерживают
`json_schema`, а отказ был бы жёстким. Парсер терпимый — `ignoreUnknownKeys`,
`coerceInputValues`, вырезание JSON из markdown-ограждения и болтовни вокруг.
На всё это есть тесты: модель регулярно отвечает не по форме.

Изображение ужимается до 1600px по длинной стороне (`MAX_SIDE`) и кодируется в base64.
Декодирование с разворотом по EXIF вынесено из `AndroidPhotoStorage` в общий
`platform/ImageDecoding.kt` — одна реализация на хранение и на отправку.

**Выбор реализации — делегатом, не фабрикой:**

```kotlin
class SwitchingLabelRecognizer(
    private val onDevice: AndroidLabelRecognizer,
    private val cloud: OpenRouterLabelRecognizer,
    private val settings: SettingsStore,
) : LabelRecognizer {
    override suspend fun recognize(source: PhotoSource): LabelScan {
        if (!settings.recognition.first().usable) return onDevice.recognize(source)
        return try {
            cloud.recognize(source)
        } catch (e: CancellationException) {
            throw e
        } catch (cloudFailure: Exception) {
            // Офлайн лучше пустоты. Но если и там пусто, причину не прячем:
            // «не прочиталось» списало бы отказ на этикетку, а дело в ключе или сети.
            onDevice.recognize(source).takeIf { !it.isEmpty } ?: throw cloudFailure
        }
    }
}
```

Делегат отдаётся через `@Provides` (ему нужны обе реализации сразу); `ListViewModel`
о выборе не знает. ML Kit остаётся в проекте: он единственный работает офлайн и без ключа.

## Настройки

Новый раздел на существующем экране (`ui/settings/SettingsScreen.kt`), между «Копия
журнала» и «О приложении», в том же стиле: `SectionLabel` + карточки `glassCard`.

Чекбокс **«Распознавание через LLM»**, подпись «Требуется интернет-соединение» —
выключен по умолчанию. Пока он выключен, поля ключа и модели не показываются вовсе.
Под ним, при включении:

- **Ключ OpenRouter** — однострочное поле, значение замаскировано (`PasswordVisualTransformation`),
  с кнопкой показа. Подпись-подсказка ведёт на `openrouter.ai/keys`.
- **Модель** — текстовое поле с дефолтом `z-ai/glm-5.3-flash`. Не выпадающий список:
  каталог OpenRouter меняется чаще, чем мы выпускаем обновления, а зашитый список устареет.
  Модель проверена на реальных этикетках из архива: кириллицу читает, принимает изображения,
  скан обходится примерно в четыре сотых цента.

Хранение — `DataStoreSettings`, отдельными ключами и отдельным `Flow`, **не внутри
`Settings`**: `SettingsStore.save` переписывает запись целиком, и сохранение категории
затирало бы ключ. Это ровно та причина, по которой `compactList` уже вынесен отдельно.

```kotlin
data class RecognitionConfig(
    val enabled: Boolean = false,
    val apiKey: String = "",
    val model: String = DEFAULT_MODEL,
)
```

Ключ не логируется, не попадает в URL и не выгружается в резервную копию журнала.
При сохранении ключ и модель обрезаются по краям: их вставляют из буфера, а хвостовой
пробел даёт 401 или 400 — отказ, по которому не догадаться, что дело в невидимом символе.

**Ключ лежит в DataStore открытым текстом — осознанно.** Файл в приватной директории
приложения, облачный бэкап запрещён целиком. Шифрование через Keystore защитило бы его
только от доступа с root или физического извлечения, а стоило бы отдельного слоя
хранения; если ключ подорожает (командный аккаунт, платный тариф) — вернуться к этому
решению.

Лимиты токенов подобраны по замерам, а не на глаз: выбранная модель — reasoning,
и размышление тратит тот же лимит. На пробе 95 из 101 токена ушло на размышление,
а `content` пришёл `null` — с прежними 1024 ответ обрывался бы до текста.

В манифест добавляется `android.permission.INTERNET` — сейчас его нет вовсе.

## Сценарии

**1. Поиск по фото** (`ListScreen`, кнопка уже есть). `ListViewModel.onScanLabel`
получает `LabelScan` и собирает запрос из **названия и типа**. Год в запрос не идёт:
он отсекал бы ту же бутылку другого урожая. `queryFuzzy = true` и `stripCameraWatermark`
остаются — они нужны ML Kit-ветке.

**2. Черновик заметки** (`EditScreen`, кнопка у поля заметки) — **в два запроса**:

- Шаг 1: короткий поисковый запрос с веб-плагином OpenRouter. Без образцов и разметки —
  иначе модель, занятая подражанием стилю, формирует невнятный поисковый запрос и
  приносит описания посторонних вин (проверено: приходили Каберне «Фанагории» вместо
  южноафриканского пинотажа). Ничего не нашлось — возвращается `НЕТ ДАННЫХ`.
- Шаг 2: изложение найденного стилем автора, без веб-поиска. Образцы — три последние
  непустые заметки той же категории.

Нашлось пусто — заметка не пишется, пользователь видит отдельное сообщение. Выдумка,
поданная как найденное, хуже честной пустоты. «Не нашлось» модель говорит маркером;
пустой ответ на шаге 1 — это отказ самого запроса, и списывать его на отсутствие
описаний нельзя.

Найденные характеристики кэшируются на сессию редактора (экземпляр `DraftWriter` живёт
вместе с ним): сбой второго шага не заставляет платить за веб-поиск заново.

Пока модель пишет, **поле заметки заморожено**: готовый ответ перезаписывает его целиком,
и набранное за эти секунды пропало бы молча. Остальные поля правятся как обычно.

Стоимость замерена: поиск $0.0074, стилизация $0.0006, итого около 0.8 цента.
Почти всё — плата за результаты веб-поиска, не за токены.

**Предзаполнение записи при добавлении фото — отменено по итогам проверки.**
Распознавание заметно дольше ручного ввода, а заполненные им поля всё равно
приходилось проверять. Вместе с ним удалены `applyScan`, флаг `recognizing`
и зависимость редактора от распознавателя.

## Ошибки

Сеть, таймаут, отказ провайдера и пустой ответ различаются для пользователя, потому что
действия разные: проверить интернет, проверить ключ, попробовать позже.

Тексты отказов общие для обоих сценариев и потому не упоминают этикетку: причина
у скана и у черновика одна, а таблица «причина → строка» — одна на все экраны
(`ui/RecognitionMessages.kt`, по итогам чистки; до неё она была разложена по трём
местам через энум-двойник в `ListViewModel`).

| Ситуация | Поведение |
|---|---|
| Чекбокс выключен или ключ пуст | Скан тихо работает на ML Kit, как сегодня; кнопка черновика не показывается вовсе — нажатие всё равно отвечало бы отказом, а объяснять настройку снекбаром не место |
| Нет сети / таймаут | Фолбэк на ML Kit; сообщение про офлайн-распознавание — одно, даже если ML Kit тоже вернул пусто |
| 401/403 (ключ неверен или отозван) | Сообщение про ключ со ссылкой на настройки |
| 402 (кончились кредиты) | Отдельное сообщение: дело не в ключе |
| 400/404 (опечатка в имени модели, модель без vision) | Отдельное сообщение про модель (`MODEL`): она — поле свободного ввода, и это самая вероятная ошибка настройки |
| 401/402 при удавшемся офлайне | Результат показывается, но причина всё равно доходит до пользователя (`RecognitionNotices`): мёртвый ключ сам не починится, а обнаружился бы только на первой кириллической этикетке |
| 429 / 5xx | «Попробуйте позже», фолбэк на ML Kit |
| Ответ не разобрался или пуст | Как отсутствие результата — и потому тоже фолбэк на ML Kit: `content: null` у reasoning-модели и битый JSON выглядят одинаково, а латиницу офлайн ещё прочтёт |
| Ответ оборван по лимиту токенов (`finish_reason: length`) | Считается пустым: обрезанный JSON не разобрать, а обрезанный черновик иначе заменил бы заметку половиной фразы |
| Модель вернула пустой черновик | Отказ причиной `OTHER`; пустая строка в заметку не попадает |
| Про напиток ничего не нашлось | Черновик не пишется, отдельное сообщение (`NO_DATA`) |

Таймаут — 45 секунд: vision на большой картинке небыстрый, а черновик ещё и ходит
в веб-поиск. Обрывать запрос, который вот-вот ответит, хуже, чем подождать.

## Тесты

Проверяемые поведения, каждое — на JVM:

- **Разбор ответа модели**: валидный JSON → заполненный `LabelScan`; лишние поля и `null`
  в поле с дефолтом не роняют парсер; мусор вместо JSON и `content: null` (штатный ответ
  reasoning-модели, когда лимит кончился на размышлении) → пустой результат, а не
  исключение; JSON в markdown-ограждении разбирается.
- **Делегат**: выключенный чекбокс → зовётся ML Kit; включённый → облако; падение облака →
  фолбэк на ML Kit; пустой ответ облака → тоже фолбэк; облако упало и офлайн пусто →
  причина доходит до вызывающего; отказ ключа при удавшемся офлайне → сигнал пользователю.
- **Поисковый запрос** из `LabelScan`: собирается из названия и типа, без года; пустая
  строка вместо `null` считается отсутствием поля, а тип без названия в запрос не идёт.
- **Настройки**: ключ и модель переживают сохранение категории и сортировки; на свежей
  установке модель — дефолтная.
- **Примеры для черновика**: DAO отдаёт непустые заметки своей категории, свежие первыми;
  ViewModel передаёт их в `DraftWriter`.

HTTP-слой целиком не мокается: тестируются сериализация, разбор и делегат — то,
где живёт логика.

## Что осталось открытым

- Черновик излагает **чужие впечатления** голосом автора: модель пересказывает найденные
  обзоры, а не его дегустацию. Как заготовка перед дегустацией — полезно; как готовый
  текст в паблик — требует правки. Это осознанный выбор, не недоделка.
- Число результатов веб-поиска (3) определяет и качество, и почти всю стоимость.
  Снижение до 1–2 удешевляет черновик вдвое-втрое ценой попаданий.
