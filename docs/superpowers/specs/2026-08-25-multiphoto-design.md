# Несколько фотографий в записи

**Дата:** 2026-08-25
**Статус:** дизайн одобрен, готов к планированию

## Контекст

Запись дневника хранит ноль или одно фото: `Entry.photoPath: String?`. Для постов
в паблик нужен набор снимков (этикетка, контрэтикетка, бокал), поэтому запись
переводится на список фотографий.

Задача выделена из более крупной — «кнопка экспорта записи и публикации
внешние приложения». Для публикации используются готовые `entry.photos`.

Лимит — **3 фотографии** на запись.

## Область

**Входит:** доменная модель, схема БД, владение файлами, редактор, карточка,
список, тесты.

**Не входит:** перетаскивание для смены порядка (обложка назначается пунктом
меню), изменения в сжатии и импорте изображений (`AndroidPhotoStorage` как есть),
показ нескольких фото в списке (там обложка), всё, что связано с ВК.

## Модель и БД

`Entry.photoPath: String?` **заменяется** на `photos: List<String> = emptyList()`;
обложка — `photos.firstOrNull()`. Не «photoPath плюс дополнительные»: два
источника правды заставили бы каждого вызывающего помнить про оба.

`EntryEntity.photoPath: String?` → `photos: String?` — JSON-массив относительных
путей, тем же приёмом, что уже применён к сортам винограда. Рядом с
`encodeGrapes`/`decodeGrapes` появляются `encodePhotos`/`decodePhotos` с той же
семантикой: пустой список → `null`, битая строка → пустой список.

`searchText` не затрагивается — пути к файлам в поиске не участвуют.

Версия БД **3 → 4**, `fallbackToDestructiveMigration` остаётся: база на устройстве
тестовая, ценных записей в ней нет. Новая схема экспортируется в `app/schemas/`,
старые `*.json` не удаляются (см. память `room-db-migrations-dev`: изменение
схемы без поднятия версии роняет Room на валидации `identityHash`).

Лимит живёт в `EntryLimits`:

```kotlin
/** Максимум фотографий в записи. */
const val PHOTOS_MAX = 3
```

### Запрос используемых путей

`EntryDao.usedPhotoPaths()` сейчас `SELECT photoPath FROM entries WHERE photoPath
IS NOT NULL`. Колонка стала JSON-массивом, поэтому запрос отдаёт сырые строки:

```kotlin
@Query("SELECT photos FROM entries WHERE photos IS NOT NULL")
suspend fun usedPhotoJson(): List<String>
```

а `EntryRepositoryImpl.usedPhotoPaths()` разворачивает их через `decodePhotos`.
Разбор в Kotlin, а не `json_each` в SQL: JSON пишем мы сами, декодер уже есть и
покрыт тестами, а зовётся это раз за запуск — из `OrphanPhotoSweeper`.

## Владение файлами

Самая тонкая часть: вся машинерия владения построена на «ноль или один файл».
`PhotoLease` внутри не меняется — счётчик аренд уже считает то, что нужно;
добавляются только тонкие обёртки `acquireAll`/`releaseAll` и
`PhotoCleaner.purgeAll`.

**`EntryRepository`:** `purgePhoto(String?)` → `purgePhotos(List<String>)`.
Возвращает `true`, если не осталось ни одного неудалённого файла.

**`DeleteEntryUseCase`:** `previous.photoPath` → `previous.photos` в `delete`,
`expire` и `clearPending`; аренда берётся и снимается на весь список.

**`EditViewModel`** — здесь изменений больше всего:

- `committedPhotoPath: String?` → `committedPhotos: Set<String>`; в
  `SavedStateHandle` уезжает массивом строк (`KEY_COMMITTED_PHOTOS`).
- `leasePhoto(path)` → `leasePhotos(paths)`: сначала `acquire` появившихся, потом
  `release` ушедших — порядок сохраняется от нынешнего кода, иначе счётчик
  одного и того же пути проседает до нуля и уборка успевает его забрать.
- `onPhotoPicked(source)` → `onPhotosPicked(sources: List<PhotoSource>)`: берёт
  не больше `PHOTOS_MAX − photos.size` источников и импортирует их
  последовательно, добавляя каждый в `entry.photos` сразу после успеха — аренда
  тем самым покрывает файл немедленно. Отменённый импорт удаляет свой файл
  (нынешняя ветка `!isActive`) и прекращает обработку остатка.
- Вытеснения импорта новым выбором больше нет: пока `photoImporting`, кнопка
  добавления недоступна. Это проще нынешней логики `photoJob?.cancel()`, а не
  сложнее.
- Сбой импорта одного файла не прерывает остальные; событие `photoError`
  эмитится один раз за пачку.
- `onPhotoRemove(path)`: убирает путь из списка и чистит файл, только если его
  нет в `committedPhotos` (иначе он принадлежит сохранённой записи и должен
  пережить отмену редактирования).
- `onPhotoMakeCover(path)`: переносит путь в начало списка. Файлы не трогает.
- `save()`: `replaced = committedPhotos − stamped.photos` → `purgeAll`;
  `committedPhotos = stamped.photos.toSet()`. Как и сейчас, под `NonCancellable`.
- `discard()`: `staged = entry.photos − committedPhotos` → `purgeAll`.
- `onCleared()`: `releaseAll` всех арендованных.

## UI

**Редактор.** `PhotoBox` превращается в `PhotoStrip`: горизонтальный ряд до трёх
миниатюр плюс плитка «+», которая исчезает на третьей фотографии и блокируется
во время импорта. Тап по миниатюре открывает существующий `SelectSheet` с
пунктами «Сделать обложкой» (скрыт для первой) и «Удалить». Новый компонент
выбора не пишется.

Галерея переключается с `PickVisualMedia` на `PickMultipleVisualMedia` с
`maxItems` = сколько осталось до лимита. Камера остаётся однокадровой и отдаёт
список из одного источника.

**Карточка.** `Hero` показывает обложку; при нескольких фото становится
`HorizontalPager` с точками-индикаторами — это компонент `compose.foundation`,
новых зависимостей нет. Полноэкранный просмотр открывает ту фотографию, что
видна в пейджере, но сам не листается: горизонтальный жест там уже занят
панорамой увеличенного снимка, и два разных смысла у одного свайпа — это ловушка,
а не удобство.

Подписи для скринридера нумеруются: «Фото 2 из 3, {название}». Точки-индикаторы
декоративны и из дерева доступности исключаются.

**Список.** Обложка вместо единственного фото — [ListScreen.kt:230](../../../app/src/main/kotlin/ru/kaufd/bodega/ui/list/ListScreen.kt) (`Hero`) и `EntryCard` около строки 580. Правка механическая.

## Тесты

Существующие тесты правятся механически: `photoPath = "photos/a.jpg"` →
`photos = listOf("photos/a.jpg")`. Новые, по TDD, в порядке написания:

- новый `EntryEntityTest`: `encodePhotos`/`decodePhotos` — пустой список,
  несколько путей, битая строка.
- `EntryDaoTest` / `EntryRepositoryImplTest`: `usedPhotoPaths` разворачивает JSON
  нескольких записей в плоский список.
- `DeleteEntryUseCaseTest`: аренда берётся на все фото удалённой записи; `expire`
  чистит все; вытеснение прежней pending чистит все её файлы.
- `EditViewModelTest`: добавление пачки, лимит в три, удаление staged-файла
  чистит его, удаление сохранённого — нет; смена обложки не трогает файлы;
  сохранение чистит только выпавшие из списка; отмена чистит только staged;
  сбой импорта одного из двух не теряет второй.

## Порядок работ

1. Модель, entity, кодеки, версия БД, DAO и репозиторий (+ тесты data-слоя).
2. Владение файлами: `PhotoLease`/`PhotoCleaner`-обёртки, `DeleteEntryUseCase`
   (+ тесты).
3. `EditViewModel` (+ тесты) — самый тонкий шаг.
4. UI: `PhotoStrip` в редакторе, пейджер в карточке, обложка в списке.

Шаги 1–3 проверяются JVM-тестами, шаг 4 — запуском на эмуляторе.

## Риски

- **Аренда во время пакетного импорта.** Файл защищён от уборки только после
  добавления в `entry.photos`. Между `importImage` и добавлением есть окно; оно
  такое же, как в нынешнем коде, и закрыто порогом возраста в
  `OrphanPhotoSweeper` (7 дней).
- **Черновик в `SavedStateHandle`.** `Entry` сериализуется kotlinx с новым полем
  `photos`; черновик, сохранённый прошлой версией приложения, декодируется в
  запись без фотографий, а не роняет экран (`ignoreUnknownKeys` уже включён).
