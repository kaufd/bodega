# Погребокъ — дизайн MVP (архитектура и решения)

> Дата: 2026-07-09. Статус: утверждён.
> Этот документ фиксирует архитектурные решения и границы MVP.
> Источник по UI/дизайну — `docs/СПЕЦ-для-агента.md` и макет `Погреб - стартовый экран.dc.html`; настоящий документ их **дополняет, не дублирует**. При противоречии по UI приоритет у СПЕЦ-для-агента, по архитектуре — у этого файла.

## 1. Продуктовая рамка

Личный дневник алкогольных напитков для одного пользователя. Три категории: вино, пиво, крепкое. Без регистрации, авторизации, бэкенда, синхронизации и социальных функций. Все данные — локально на устройстве.

## 2. Скоуп MVP

**Входит:**
- CRUD записей (создание, просмотр, редактирование, удаление с подтверждением и undo)
- Главный экран 6a: список, поиск, таб-бар категорий
- Полноэкранные фильтры + сортировка
- Пустые состояния 8a / 8b / 8c
- Фото: photo picker / камера, хранение во внутреннем хранилище

**Не входит (этап 2 и далее):**
- Экспорт в JSON — но модель данных и слой data готовятся к нему сразу (kotlinx-serialization в зависимостях, доменные модели сериализуемы)
- Поиск по загружаемой фотографии
- Десктопное приложение (вероятность низкая; см. «KMP-гигиена»)

## 3. Стек

| Область | Решение |
|---|---|
| Язык / UI | Kotlin, Jetpack Compose, Material 3 (полностью перекрашен токенами из СПЕЦ) |
| БД | **Room 2.8.x через SQLiteDriver API** (`BundledSQLiteDriver`), не legacy SupportSQLite — дешёвый переезд на Room 3.0 и в KMP |
| DI | **Hilt** (выбран осознанно: привычность; известная цена выхода при KMP-выносе ≈ полдня механической миграции «всё или ничего») |
| Навигация | Navigation Compose |
| Изображения | Coil 3 |
| Настройки | DataStore (Preferences) |
| Сериализация | kotlinx-serialization (задел под экспорт) |
| Арх. линтер | Konsist (`testImplementation`) |

## 4. Архитектура

Один модуль `:app`, MVVM + Repository. Пакеты:

```
ru.kaufd.bodega
├── domain/        # модели (Entry, Category), интерфейсы (EntryRepository, PhotoStorage),
│                  # справочники подсказок типов/сортов/стран
├── data/          # Room: entity, DAO, database; EntryRepositoryImpl; DataStore-обёртка
├── platform/      # AndroidPhotoStorage: файлы фото, glue для photo picker/камеры
├── ui/
│   ├── list/      # главная 6a: поиск, список, таб-бар, пустые состояния
│   ├── detail/    # карточка записи
│   ├── edit/      # создание/редактирование
│   ├── filters/   # полноэкранный экран фильтров
│   └── theme/     # токены: цвета, шрифты Cormorant/Spectral/IBM Plex Mono
└── di/            # Hilt-модули
```

### KMP-гигиена (энфорсится Konsist-тестами)

1. Пакеты `data` и `domain` не импортируют `android.*` (исключение: `androidx.room.*` — KMP-совместимы).
2. Направление зависимостей: `ui → domain ← data`; `domain` не зависит ни от кого.
3. Работа с файлами фото — только через интерфейс `PhotoStorage` (объявлен в `domain`, реализован в `platform`).

Konsist-тесты — обычные unit-тесты, падают в `./gradlew test`. Точный API сверить с актуальной документацией Konsist при написании.

## 5. Модель данных

Одна таблица `entries`. Поля — по разделу 2 СПЕЦ-для-агента (общие + категорийные `grape / country / vintageYear / style / ageStatement` как nullable-колонки). Рейтинг — целое 1–10.

Решения поверх СПЕЦ:

- **Тип / сорт / страна — гибрид:** предзаполненные справочники подсказок на категорию (константы в `domain`) + свободный ввод. В базе хранится строка. UI: поле ввода с чипами/автодополнением из справочника и ранее введённых значений.
- **Фильтры строятся из фактических значений в базе** (`SELECT DISTINCT`), не из справочника.
- **Поиск** — по `name`, `type`, `grape`/`style`, `country`. Заметка не участвует. Обычный `LIKE` без FTS (масштаб — сотни записей).
- **Фото:** файл во внутреннем хранилище `files/photos/{uuid}.jpg` (сжатый), в базе — относительный путь. Удаление записи удаляет файл (после истечения undo).

## 6. Поведение экранов

Экраны и визуал — по СПЕЦ-для-агента (6a, карточка, редактор, фильтры, 8a/8b/8c). Уточнения:

- **Комбинация ограничений списка:** таб-бар задаёт категорию; поиск и фильтры действуют внутри неё; таб «Все» — без ограничения категории. Бейдж на кнопке фильтров — число активных фильтров (без учёта категории таба).
- **Персистентность:** последняя категория и сортировка переживают перезапуск (DataStore). Поисковый запрос — нет.
- **Удаление:** диалог подтверждения → Snackbar с undo (~5 сек); физическое удаление файла фото — только после истечения undo.
- **Редактор:** «Отмена» при несохранённых изменениях → диалог «Выйти без сохранения?». Смена категории в сегменте меняет набор полей; уже введённые общие поля сохраняются, категорийные — очищаются при подтверждении смены.
- **Обязательные поля:** только название и категория. «Сохранить» неактивна без названия.

## 7. Тестирование

- **Unit:** репозиторий с in-memory Room; DAO-запросы фильтрации/поиска; ViewModel (состояния списка, комбинация фильтров).
- **Konsist:** архитектурные правила из раздела 4.
- **UI (Compose):** точечно — редактор (смена категории меняет поля), экран фильтров. За покрытием не гонимся.

## 8. Открытые решения, отложенные сознательно

- Формат экспорта JSON (схема, вопрос фото в экспорте) — решается на этапе 2.
- Миграция на Room 3.0 — когда выйдет stable; выбор SQLiteDriver API делает её дешёвой.
- KMP-вынос под десктоп — только если десктоп подтвердится; путь: `:shared`-модуль, перенос `data`/`domain`, миграция с Hilt (≈ полдня).
